## Project status

FinSight is an IIT Kharagpur capstone (Track B · API-side): a multi-agent copilot that answers questions about US companies' SEC 10-K/10-Q filings, with citations and verified calculations, running on a hosted ≤8B chat model plus an embeddings endpoint. Fine-tuning and larger models are not allowed. Quality has to come from retrieval, tools, orchestration and evaluation.

## Architecture (planned)

```
Streamlit UI → FastAPI /ask (rate limit + cache) → LangGraph app
  Planner → [Research agent (search_filings) + Data agent (get_financial_fact) + Analyst (calculate, writes answer)] → Critic → answer contract JSON
```
- **core/llm.py** (exists) is the only LLM access point, async: `chat(messages)`, `chat_json(messages, PydanticSchema)` → validated object (validate, then re-prompt with the error, at most `LLM_JSON_RETRIES`=2 retries), and `embed(texts)` → one vector per text (OpenAI-compatible endpoint or local sentence-transformers). Calls, tokens, JSON retries, seconds and embedding requests accumulate in `client.usage`. Use it as `async with LLMClient(get_settings()) as llm:` so HTTP connections close before the event loop ends. Settings come from `core/settings.py` (`get_settings()`), configured only through `.env` (shell environment variables override it): `LLM_*` (incl. `LLM_MAX_COMPLETION_TOKENS`, sent as `max_tokens`), `EMBED_*`, `SEC_USER_AGENT`, `MAX_AGENT_STEPS`, `MAX_TOKENS_PER_QUERY`, `QUERY_TIMEOUT_S` (60 s, spec §9). Ollama (`llama3.2:3b`) is the local stand-in; Week 1 moves to the provided endpoint (`Qwen/Qwen3-8B`, OpenAI-compatible HTTPS with a group CA certificate; setup in LOCAL_SETUP.md "Hosted endpoint"). `LLM_CA_CERT` (PEM, relative paths from the repo root, git-ignored `certs/`) makes the chat client, and the embeddings client when it targets the same server, verify against exactly that CA (`build_ssl_context`); verification is never switched off, a CA with an http:// URL is a settings error, and a failed handshake is `TLSError`. The course's embedding endpoint (W1-16) is another server with its own CA: `EMBED_CA_CERT` (`core.llm.embed_ca` picks EMBED_CA_CERT, else LLM_CA_CERT on the same server, else the default store); `EMBED_MAX_INPUT_TOKENS` cuts texts with the pinned bge tokenizer (`core.tokens.cut_to_embedding_tokens`); embedding requests get the same retries, no queue. `LLM_ENABLE_THINKING` (default false; empty = not sent) is sent as `chat_template_kwargs.enable_thinking` (Ollama ignores it; the provided endpoint ignores it too and always answers without reasoning, measured 10 Nov), and `strip_thinking` removes `<think>` blocks from every reply and before JSON extraction. `LLM_API_KEY`/`EMBED_API_KEY` are `SecretStr` (never in a repr or error message). Shared-key rules (W1-02, week1_plan §2.2): one request at a time per endpoint server in a process, first come first served (starts ≥ `LLM_MIN_INTERVAL_S` apart; other servers, e.g. local Ollama, run in parallel), retries of 429/5xx/timeouts/network errors after 2/4/8 s (ours; the SDK's `max_retries=0`), a disk cache in `data/cache/llm/` (`LLM_CACHE_DIR`; key includes server, model, messages, temperature, max_tokens, thinking and `sample`; empty replies and errors are not cached), and a prompt-size check before sending (`count_prompt_tokens`: 7 + 5 per message + content, exact on the endpoint; `LLM_CONTEXT_TOKENS`=8192). `complete()` returns a `Reply` (text, raw, tokens, cached, retries, seconds) for runners; `chat()` returns its text. Endpoint limits: one active request per team key, 60 requests/min, 8,192 tokens per call (input + output), no embeddings there (embeddings: the separate endpoint, bge-small-en-v1.5, 16 texts and 512 tokens per request, the index's model since the W1-04 rebuild, ADR-021; BAAI/bge-small-en-v1.5 locally gives the same vectors). The key, URL and certificate never go into git, logs or screenshots. Switching models must mean editing `.env` only, so always use the `openai` client and never a provider-specific SDK.
- **core/tokens.py** (exists): `count_tokens(text)` in Qwen3-8B's own tokenizer (pinned revision; exact against the endpoint). Use it for every token budget: filing text runs 2.2 (tables) to 4.6 (prose) characters per token, so no fixed ratio is safe under the 8,192-token limit.
- **Retrieval**: BM25 (rank_bm25) plus dense (Chroma, cosine), fused with RRF (`Σ 1/(60+rank)`, top 50 from each). Metadata filters (ticker, fiscal_year, fiscal_period, form, item) are the biggest accuracy win. Default (ADR-017, W1-05): C3 hybrid with the company, year and fiscal period read from the question (`retrieval/entities.py`; the planner passes them) and, for a figure question with a period, the statement Item's chunks first (`retrieval/statement.py`): recall@5 0.986, figure@5 31/59. A cross-encoder rerank of the hybrid top 30 (`retrieval/rerank.py`) finds more answer-bearing chunks (figure@5 42/59) but adds ~4-6 s per search, so it is opt-in (`RETRIEVAL_RERANK=true`; model ~91 MB, downloaded on first use). There are three chunking variants, C1 fixed, C2 section-aware and C3 table-aware, and all three are kept for comparison. Each indexed chunk text starts with a context header such as `[AAPL 10-K FY2024 · Item 7 · MD&A]`. Chunk IDs are deterministic (doc_id + variant + number). Indexing is idempotent: delete and recreate the collection rather than appending. The Chroma collection records its embedding model (`EMBED_*` in `.env`); searching with another model is an error. `retrieval.common.Filters` validates filters and `SearchResult` carries the `search_filings` fields (week0 §2.3).
- **Tools** (exist, `tools/`; signatures fixed in week0_plan §2.3, ADR-014): `search_filings`, `get_financial_fact`, `calculate`, `compare_periods`. Each validates its arguments with a strict pydantic model that also generates its JSON schema (`tools.registry.SCHEMAS`; W2-03, ADR-026: `metric` is an enum of the concept map's metrics, 17 since W3-04 (ADR-040), with a short glossary, the calculator's operations have a line and an example each); `tools.registry.call_tool(name, arguments)` is the agent's single entry point (arguments as a dict or the JSON string of an OpenAI tool call); async code must use `call_tool_async` (the search embedder runs its own event loop), and `warm_up()` runs one search at start-up so the index and the embedding model (~15 s through the endpoint, ~40 s with a local model on a CPU) are loaded before the first question. Tools never raise into the agent: failures are `{"error": {"type", "message"}}` with types `invalid_input`, `undefined`, `not_reported` (incl. Q4), `out_of_corpus`, `data_missing`, `no_results`, `service_unavailable`, `internal_error`, so the planner can replan; a refusal (policy) and `not_reported` (data) stay distinct. `calculate` accepts only whitelisted operations (ratio, percent, growth, difference, sum, cagr), never `eval()`s model text, takes chronological inputs ([old, new]) and rounds half-up (% 1 decimal, ratio and per-share 2); ratio, percent, growth and cagr set their own unit, so an input unit given to them (e.g. 'USD millions') is not used, while a different derived unit ('%' for ratio, 'ratio' for percent) is invalid_input (difference and sum use the given unit); the critic recomputes with `tools.calculator.compute`. Figures outside the mapped metrics (e.g. Costco "net sales", a segment's figures, UNH's medical care ratio) come from cited filing text via `search_filings`, never from a different metric.
- **Agent graph** (exists, W2-01; end to end on the real nodes since W2-07): `agent/graph.py` is a LangGraph `StateGraph` over `agent/state.py`'s `AgentState`: planner → executor → composer → critic → finish. Conditional edges: a refusal plan skips the executor; a typed tool error goes back to the planner once (`MAX_PLANS`=2), a second one goes to the composer (answered as not found); a failed critic verdict goes back to the executor once (`MAX_CRITIC_RUNS`=2; a failed refusal goes back to the composer), a second failure ends unverified; no plan, no draft, a node's `stop_reason` or a broken limit (more tool calls than `max_steps`, more tokens than `max_tokens`) goes straight to finish. `finish` writes the only output, an `AnswerContract` (`with_verification`; no draft = the give-up answer with a "could not verify: ..." note naming why; a node's `stop_reason` is noted as `stopped:`, a broken limit as `limit:`; a draft the critic passed stays verified when the critic's own tokens then break the budget, with a "limit reached after the answer was checked: ..." note, spec §9). `run(question, history, limits=Limits.from_settings(...))` puts the limits in the state (`state["limits"]`, read by routing and by nodes: the executor stops itself at `max_steps - len(tool_results)`), wraps the run in `timeout_s` and returns `AgentRun(answer, state, seconds)`; a timed-out run keeps the state reached so far, a node's own `TimeoutError` propagates. LangGraph's recursion limit (13) is a backstop above the longest legal run (10 node runs, 11 LangGraph steps with the input). The graph owns the bounds and the verdict: it counts node runs (`state.visits`), rejects a node that writes `answer`, `visits`, `limits`, `question` or `history`, lets only the critic write `verdict` (a `Verdict`; a critic run without one fails the check), clears the old plan when a replan writes none and the old verdict when a new draft is written. `initial_state` resets every per-question field (writing None resets a reducer field), so a checkpointer thread that keeps a conversation never carries counters, tool results or a verified draft into the next question; give a checkpointer `serde=checkpoint_serde()` so the state's types restore (each round-trips equal, tested; `Entities` normalises its fields to tuples). Messages: `Plan` (reasoning first; a refusal has a rule and no steps or calculation; a partial refusal has a rule and steps for the factual part; `calculation` names the operation the executor runs on the fetched figures, since a plan has no numbers; steps use only `search_filings`, `get_financial_fact` and `compare_periods`, each validated against the tool's own model; `plan_json_schema()` gives strict guided decoding one step variant per tool with that tool's argument schema, with `item`, `metric`, `ticker` and `query` narrowed), `PlanStep`, `ToolCall`, `ToolResult` (`error_type`), `Verdict` (critic violations without invariant 7). (The unused `messages` field, chat messages for native tool calling, was removed in W3-07: the executor runs the plan's steps itself.) `build_graph()` uses the real nodes (`agent/nodes.py` `real_nodes(llm=None, call_tool=None)`, W2-07, ADR-031; a script should open the client itself, `async with LLMClient(settings) as llm`, and pass `real_nodes(llm)`, as `scripts/ask.py` and `eval/run_demo.py` do, so it is closed in the run's event loop); the stubs (`agent/stubs.py`: entities via `retrieval.entities.from_turns`, no steps, a placeholder draft, the real critic) stay for offline tests, which pass them explicitly.
- **Executor** (exists, W2-04, ADR-028): `agent/executor.py` `make_executor(call_tool=None, count_tokens=None)` is the node for `Nodes(executor=...)` (defaults: `tools.registry.call_tool_async` and `core.tokens.count_tokens`; offline tests pass fakes). It runs the plan's steps in order and returns only the round's new `ToolResult`s (`tool_results` is append-only); when `plan.calculation` is set it builds the `calculate` call from the fetched figures (`calculation_call`: each figure kept with its company, metric, period and duration, counted once; one unit, one duration and no missing planned figure (a gap inside a trend excepted); growth/cagr on exactly one series, oldest to newest (cagr: the same period each year, with `years`); percent = [part, the company's revenue] and ratio in step order, both for one period; difference chronological in one series, step order between companies; sum of balance-sheet values at one date; the shared unit for difference/sum; anything else = no calculation and an `errors` note). Guards: the step cap over all rounds, the token budget (LLM tokens plus the tokens of the tool output fetched so far, which the composer's prompt will carry; not added to `state["tokens"]`), (a plan step stopped by either ends the round with a `stop_reason`; a calculation stopped by one is skipped with a note), and the loop guard (a call is never sent twice: a repeat of a successful call reuses its result, a repeat of a failed one is skipped with a note while the plan's other steps run, except one more try for `service_unavailable`; only a new error sets `tool_error`). The first typed error stops the round and sets `tool_error` (one replan); `not_reported` and `undefined` are answers, not errors. A not_reported fact (a `get_financial_fact` error, or a `compare_periods` year missing as not reported) is followed, after the calculation, by the statement it was checked on (`checked_section_call`: the statement `config/concept_map.yaml` places the metric on, searched in that filing's Item 8, or Part I Item 1 of a 10-Q, the 10-K for Q4; W2-07, ADR-031), so the answer can cite the section checked (spec §5).
- **Tracing** (exists, W2-08, ADR-029): `core/tracing.py`. Off unless the caller passes `TraceInfo(question_id, run_id, session_id)` to `agent.graph.run(..., trace=info)` (and `LANGFUSE_ENABLED=true` with both keys in `.env`; tests pass `tracer=` a fake). Then one Langfuse trace per question tagged `q:<id>`, `run:<id>`, `verdict:<verified|unverified|refused>`, with a span per node run and per tool call and a generation per LLM call (`LLMClient.complete`); the run's summary (seconds, tokens, tool calls, visits, stop_reason, notes) goes on the trace's metadata. Everything sent passes `scrub` (e-mails and phone numbers masked, long text cut); a Langfuse failure is logged and never changes an answer. Without a trace every `span()`/`generation()` is a no-op (no settings read, no import, no network); CI does not install `langfuse`. The team's project is on Langfuse Cloud (Hobby, US region); `scripts/trace_dashboard.py` reads it through `GET /api/public/v2/observations` (the v1 trace list is gone), and traces sent by the v3 SDK become readable a few minutes (~8) after a run.
- **Composer** (exists, W2-06, ADR-030): `agent/composer.py` `make_composer(llm)` is the node for `Nodes(composer=...)`. values, citations and calculations come from the current plan's tool outputs through the contract builders; the model writes only the prose (one guided call, `agent/prompts/composer.txt`, pinned by PROMPT_SHA256) from figures written as the answer must show them (`display`), and may add a figure read from a passage only if it is printed there for the passage's own fiscal year and stated; a dollar or percent prose figure that a passage the answer names (else another shown passage of the same filing, then cited; W3-05) prints for its own year at the same precision (also a table cell under a declared "in millions", aligned with the year header) is backed automatically, never a count (`belongs_to_year` is conservative on purpose). The draft is checked for invariants 1, 2, 6, a citation and the operation, asked again once, then keeps only its backed sentences if they still state every fact value, else falls back to a template from the figures; when its backed sentences already pass and state every fact value, they are kept without asking again (no figure missing, W3-07); only passages of the question's companies and periods are shown (the ones the critic lets it cite, W3-07); on a send-back whose rewrite fails and whose figures give no answer, the previous draft is kept (unverified) instead of "did not find" (W3-05). Passage ids ("as stated in P3") are taken out of the prose. A "what drove X" answer opens with X's change as a passage states it, then the passages' drivers (prompt rule 10, W3-05, ADR-041). A refusal plan gets the §6 sentence with no call; a partial refusal gets one declining sentence added; a "not reported" fact is cited by the page of the statement it was checked on (W2-07). Only the critic sets verified.
- **Memory** (exists, W2-06, ADR-030): `agent.graph.run(question, history=None, graph=build_graph(nodes, checkpointer=in_memory_checkpointer()), config=thread(session_id))` takes the earlier questions from the checkpointer thread (`thread_history`; `cap_history`: the last `MAX_HISTORY_TURNS` = 6 plus the older turns that named the company, year or period); follow-ups keep the company, year and period through `retrieval.entities.from_turns`; an explicit `history` is used as given. In memory: lost on restart. The API (W2-09) keeps each session's questions itself and passes them as an explicit history, one question at a time per session (ADR-032).
- **UI** (exists, W2-10, ADR-033): `ui/app.py` (Streamlit) calls only the API through `ui/client.py` (`ApiClient.ask(question, session_id)` -> `Reply`, every error a message, never an exception; only session ids with the API's shape are kept; `health()`; one shared client), keeps the conversation in a `Conversation` (messages, latest `X-Session-Id`, pending question) and asks in two runs: the question is stored and the question box and examples disabled (New conversation stays enabled), then the next run asks and records the reply on that object without touching `st.session_state` (Streamlit stops a run at any st.* call or session-state access once the user clicks, which would lose the answer); anything the call raises is recorded as an error reply. Each answer is rendered with `ui/render.py` (plain functions, tolerant of odd fields: the verdict badge with the refusal reason in words, model text escaped with URLs as code spans, calculation, figures, SEC-only citation links with numbered passages, notes, the Show trace expander, an optional Langfuse sessions link by the id's hash, none for a cached answer). Sidebar: disclaimer, API status (cached 15 s while ready, 5 s otherwise), New conversation, the scope from `config/companies.yaml`, example questions. No agent import: streamlit, httpx and pyyaml only. Tests drive it with Streamlit's AppTest and a fake API client.
- **API** (exists, W2-09, ADR-032): `api/main.py` `create_app(graph=None, config=None, warm_up=None)`; `app` for uvicorn. One compiled graph on the real nodes and one LLM client for the app's lifetime; `tools.registry.warm_up` on a thread at start-up (/health: starting, ok or degraded; the real warm-up loads the facts, the index and one search, the agent's prompts, schemas and config files (`agent.nodes.warm_up`, W3-07) and the tokenizer); /health also shows the answer cache's hits, misses and hit rate since start-up, and the UI shows the rate under the status (W3-07). `POST /ask` returns {session_id, cached, seconds, history, answer: AnswerContract, run: verdict, steps, tokens, seconds, visits, tool calls}. Session ids are issued and signed by the server (an unknown id starts a new session); an id is a bearer token, so logs, limit keys and traces carry only its hash. /health is 503 until ready. Sessions (`api/sessions.py`): the earlier questions kept per `X-Session-Id` (capped by `cap_history`), a body `history` replaces them, a retry of the last question is the same turn, one question at a time per session. Reply cache (`api/cache.py`): normalised question + normalised history, only verified answers and refusals, bounded and expiring. Rate limits: slowapi per session (a new conversation gets its own bucket) and per address (the ceiling), 429 with Retry-After. At most `API_MAX_CONCURRENT` runs at once (503 after `API_QUEUE_TIMEOUT_S` waiting); invalid input 422; agent errors a generic 500. Tests use `create_app(graph=build_graph(fake_nodes), config=ApiConfig(...))`; no .env is read at import.
- **Critic** (exists, W2-05, ADR-027): `agent/critic.py` `make_critic()` is the node for `Nodes(critic=...)`; `critique(state)` has no LLM: `check_contract` (ADR-022; calculator recompute is already W1-07) plus unit flags against draft-used fact rows (ticker/year/period/duration/metric-or-label; does not rewrite the draft) and metric-vs-question on those same rows (so a send-back can clear a stale wrong fetch; search-only line items; follow-ups use history). Writes only `verdict`; the graph owns the one send-back and `with_verification`.
- **Planner** (exists, W2-02, ADR-025): `agent/planner.py` `make_planner(llm)` is the node for `Nodes(planner=...)`; `plan_question()` does the work, shared by the node and `eval/run_planner.py`: entities via `from_turns`, with years used as dates dropped (`planning_entities`); one strict guided call (`agent/guided.py` `ask_guided`, re-asked once with the validation error; a failed call or a second invalid reply means no plan, so the graph gives up); one more call when an R3 refusal contradicts the indexed scope (`scope_contradiction`, not for forecasts, live prices or news); then `finalize`, whose rules correct the model only where the question shows it is wrong: `scope_check` (every named period unindexed -> R3, or R2 for a question about the future), `company_scope` (W3-04: every step for a ticker outside the corpus while the conversation names no indexed company -> R3, or R2), `refusal_rule_check` and `partial_refusal` (W3-06, ADR-042: the critic's refusal-rule checks on the plan; R6 for an instruction to ignore the rules or change role, whatever it asks, refused whole; R7 not R5 for tax or legal advice; R2 not R3 for a forecast; a refusal under R1/R2/R4 of a question that words the refused part and also asks for a reported figure becomes a partial refusal with fact steps for the named metrics, companies and indexed years, declined under the rule the question words, within the step cap), `search_only_steps` (W3-04: a fact step standing in for a search-only line item such as stock-based compensation becomes a search for it, the critic's `SEARCH_ONLY` rule), `apply_entities` (every search covers the question's companies; empty years and periods filled), `normalize_arguments` (no period cue in the conversation -> every step for the fiscal year, otherwise the model's period stands; a search's form follows its period; `k` = 5 and `duration` left to the tool; a guessed `item` and redundant `compare_periods` dropped), `mdna_searches` (W3-05, ADR-041: a "what drove X" question, `critic_checks.DRIVERS`, searches the MD&A of its period, Item 7 / Part I Item 2, with X in the query), `step_scope` (steps for unindexed filings dropped, the rest answered as a partial R3/R2, nothing left = a refusal), `align_calculation` (the operation `critic_checks.expected_operations` expects, e.g. a margin is `percent`), then duplicates removed and the plan validated again. `PROMPT_SHA256` pins everything the model sees (the system prompt from `agent/prompts/planner.txt` with the scope, tools and metrics filled in, the decoding schema, every message template; tested), so the same pin means the same requests; `rules_sha256()` records the rule code per run (its tokens without docstrings or comments; the same value on Python 3.12+). After a change to what the model sees, re-tune (`python eval/run_planner.py --run P<n>`, development questions only: `eval/dev_set.jsonl` and `eval/planner_dev.jsonl`, kept apart from gold-v1 and the test sets by a test) and re-pin.
- **Agent robustness**: every control-flow LLM output is Pydantic-validated JSON. There is a hard cap of 10 steps per query and each query has a token budget (~12k) and a 60 s timeout (enforced by the W2-01 graph); repeated identical tool calls are detected (W2-04 executor: never sent twice; a repeated successful call is reused, a repeated failed one is skipped). The critic (W2-05) checks that every number appears in a tool result or a cited chunk, recomputes every calculation, checks company/year/period and refusal policy, owns units against tool facts, and flags a wrong-metric fetch; on failure the graph sends the answer back once, then answers "could not verify".

## Data contracts (shared across work packages: don't change them unilaterally)

- `data/sections/sections.jsonl`: one Item section of one filing per line. This is the "document" unit, and the corpus must have 500–2,000 of them. `doc_id` looks like `AAPL_10-K_2024_Item7` (10-Q: `AAPL_10-Q_2025Q1_PartIItem1`). The full field list is in week0_plan §2.1.
- Item naming is exact: `"Item 1"`, `"Item 1A"`, `"Item 7"`, `"Item 8"`. 10-Qs use `"Part I Item 2"`. The gold set uses the same strings.
- `data/xbrl/<TICKER>.json` holds raw SEC companyfacts. `config/concept_map.yaml` (exists) maps 17 metric names (13 until W3-04 added deposits, noninterest_expense, current_assets and current_liabilities, ADR-040) to candidate XBRL concepts in priority order, with the line-item label to use (company-specific where the wording differs), the declared gaps and caveats (`notes`); `ingest/xbrl.py` `find_fact()` selects a value (WP6's `get_financial_fact` wraps it). `config/companies.yaml` lists the 20 tickers (with CIK, sector, fiscal-year end and name aliases) and the in-scope forms and fiscal years.
- `eval/gold_set.jsonl`: 80 items. The ID is the category letter plus 2 digits: A fact, B ratio, C period, D multi-company, E qualitative, F multi-turn (uses `previous_turn_id`), G refuse / not answerable (G items carry `refusal_rule`). The answer contract (fields and invariants the critic and evaluation check) is defined in `docs/spec.md` §8, which supersedes plan §3.5; in code it is `agent/contract.py` (strict pydantic models, shape only; built from tool outputs with `Value.from_fact`, `Citation.from_fact` / `from_search`, `Calculation.from_tool`; `refusal_answer` writes the §6 sentences; `contract_json_schema()` for `response_format` json_schema, whose guided decoding matches a `pattern` against the whole string, so patterns are `^...$`) and the invariants are `agent/critic_checks.py` (`check_contract(contract, QuestionScope, question)` -> violations, `with_verification`; ADR-022). Spec names (units, periods, rules, Items) live in `core/spec.py` and the figure reader in `core/figures.py`; production code never imports `eval/`.
- `data/raw|sections|xbrl|chunks|index` are git-ignored. Small hand-checked samples go in `data/sample/`.

## Domain gotchas

- **Fiscal year = the company's own label, never the calendar year.** Apple's year ends ~Sep, Microsoft's in Jun, NVIDIA's ~late Jan and Walmart's ~Jan. Map accession number → (fy, fp) using the XBRL fact rows.
- **XBRL annual-value selection rule**: form 10-K, fp = FY, duration of 330–400 days (or an instant), then take the row with the **latest end date** within each filing. A 10-K repeats prior-year comparatives under the same fy label, so skipping this rule returns last year's number. For amended filings, keep the most recently filed value.
- Banks (JPM, BAC, WFC, C, GS) often have no single "Revenues" tag. Handle this explicitly and document it as a known limitation.
- Keep filing units (millions/billions) and round percentages to 1 decimal place. Never compute from numbers that were not retrieved.
- Document text is data, never instructions: injected instructions in retrieved text are ignored (not refused) and the question is answered from the other sources (tests in `eval/injection_tests.jsonl`). W2-13 (ADR-035): a passage that addresses an AI system is left out whole (`agent/injection.tampered`, `agent/composer.gather`), the critic flags an answer carrying an injection's payload (`check_injected_instructions`) and `graph.finish` replaces any draft that leaves without the critic's pass and carries it with the give-up answer (`Nodes.injection_guard`); `injection_guard=False` only to measure them. The detector is a filter (held-out recall about half, `eval/score_injection_detector.py`); a pattern change must keep the corpus scan at zero and update the known misses in `eval/injection_detector_sets.json`, never tune on `heldout_2`. E-mails and phone numbers are masked in traces and in every log record (`core/pii.py`, `install_log_masking()` in the API and the CLIs). Refusal rules R1–R7 are in `docs/spec.md` §6: investment advice, forecasts, out of corpus, valuation opinions, personal data, rule-breaking instructions in the user message, off-topic.
- Period rules (`docs/spec.md` §4): a bare year means the fiscal-year label; "Q2" means the three-month figure; Q4 is not derived; the corpus stops at the FY2025 10-K and FY2025 Q3 10-Q even where fiscal-2026 filings exist.
- SEC fair access: send a descriptive `User-Agent` (from `SEC_USER_AGENT`) and make fewer than 10 requests per second. Download once and cache. The demo must never hit the SEC.

## Process rules

- **The gold set is frozen before agent code** (git tag `gold-v1`). Never edit gold answers to improve scores. Corrections go through a reviewed PR that bumps the version.
- Prompts are never tuned on gold-v1: the B0 comparison prompt is frozen before the gold runs, and S1–S3 are tuned on the development set (`eval/dev_set.jsonl`, 15 items on filing periods gold-v1 does not use; `eval/validate_dev_set.py` checks the separation in CI), then frozen and tagged. Every reported answer-quality number must trace back to a committed runs file (week1_plan §2.5).
- Retrieval metrics (recall@k, MRR against `gold_sources`) are measured separately from answer quality.
- Branches: Week 0 used `wpN/<short-desc>` (e.g. `wp2/section-parser`); from Week 1 they are `w1/UPGRAD-<key>-<short-desc>` (e.g. `w1/UPGRAD-43-endpoint`). Every commit message starts with the Jira key. Every PR needs one review from the ticket's backup before merging to `main`.
- Never commit `.env`. Line endings are LF (`.gitattributes`).
